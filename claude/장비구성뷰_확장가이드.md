# 장비구성뷰 확장 가이드 (새 채팅용)

이 문서는 "고장분석 프로그램" 프로젝트에서 **장비구성뷰**(시스템 지도 → 랙 구성 → 보드 열/프레임 → 보드 상세 → 전원흐름)를 만들 때 썼던 작업 규칙을 정리한 것입니다. (2026-09-07 최초 작성 → 2026-09-16 갱신: 남은 그룹 6개가 모두 완료되어 §1을 현재 상태로 갱신)

**2026-09-16 기준 안내**: 아래 §1이 말하는 "남은 6개 그룹"은 전부 완료되어, 이 문서가 원래 다루려던 확장 작업 자체는 끝났습니다. 이 문서는 이제 (a) 완료 이력 참고용, (b) **앞으로 새로운 그룹·새로운 데이터 종류가 또 추가될 때** 같은 패턴(§2~5)을 재사용하기 위한 규칙집으로만 남겨둡니다.

---

## 1. 지금까지 완료된 것 (2026-09-16 기준 — 전체 완료)

**최신 화면: `장비구성뷰_v3_시안.html`** — 아래 12개 그룹 전부가 하나의 통합 화면(시스템 지도/랙 구성/전원흐름/측정지점/고장상황 5탭)에서 보입니다.

**실제 캐비닛 배치 자료 완료(`kind: 'cabinet'`) — 12개 그룹 전부**: SICAS, EC/DSTT, FTGS(AF궤도회로), LZB700M, ATO Loop 제어함, IFC, TWC, PSD 인터페이스, 분기부 안전설비, 분전반(AC), 분전반(DC), 전원장치(UPS). `rack-layout.json`에 그룹별 row 기반 실제 캐비닛 구성(전면/후면/현장설비 등)이 전부 들어있습니다.

과거(2026-09-07 시점)에는 "SICAS·EC/DSTT만 완료, 나머지 6개는 kind:'concept'(개념도)"였으나, 이후 여러 세션에 걸쳐 FTGS·ATO Loop 제어함(09-07), LZB700M(09-07), IFC/TWC/PSD 인터페이스/분기부 안전설비 + 분전반(AC)/(DC)/전원장치(UPS)(09-08)가 차례로 실제 자료 기반으로 승격되어 지금은 남은 그룹이 없습니다. 세부 경위가 궁금하면 프로젝트의 최신 인수인계서(`claude/장비구성뷰_UI개선_인수인계서_갱신본_*.md`, 가장 최근 날짜 파일)를 참고하세요.

**`claude/device-connections.json`**: 시스템 지도의 노드/엣지 전체가 여기 있습니다. 새 그룹·새 연결을 추가할 때는 이 파일을 먼저 읽어 이미 있는 노드에 살을 붙이는 식으로 진행하고, 중복 노드를 만들지 마세요.

## 2. 작업 순서 (새 그룹이 또 생기면 이 순서를 그대로 따르면 됩니다)

1. `claude/board-info.json`을 project_read해서 해당 그룹의 보드 목록·기능 설명이 이미 있는지 확인.
2. 사용자가 제공한 캐비닛/보드 사진·도면(하드웨어 설계자료 PDF 등)을 보고 실제 물리 배치(랙 안에 보드가 어떤 순서로 있는지, 채널 반복 구조가 있는지)를 확인.
3. `claude/rack-layout.json`을 project_read → 기존 내용 유지한 채 **새 그룹 키 추가** → 전체를 다시 project_write. **절대 기존 그룹을 지우거나 통째로 새로 쓰지 말 것.** row 기반 `boards` 배열(전면/후면, `boardRef`/`count`/`frameRef`/`channel`/`measurePointRef`)을 그대로 재사용할 것 — 이미 검증된 스키마임.
4. LED 정보가 있는 보드는 `claude/board-face.json`에 정밀 좌표를 추가해도 되지만, **필수는 아님** — board-info.json에 구조화 `ledInfo`({id,label,section,meaning,normalState})만 있으면 v3의 자동 보드 얼굴 렌더러가 세로형으로 알아서 그려줌.
5. `claude/device-connections.json`을 project_read → 이 그룹과 다른 그룹/기기 사이의 연결(케이블 종류, 경유장치, 프로토콜)을 노드·엣지로 추가 → 전체를 다시 project_write. 케이블 종류는 `cable` 필드에 실제에 맞는 표현을 쓸 것 — v3가 이 문자열로 시스템 지도 선 색을 자동 매핑함(`cableColor()` 참고).
6. `장비구성뷰_v3_시안.html`을 project_read해서 로컬에 저장 → `GROUPS` 객체에서 해당 그룹의 `kind`를 `'cabinet'`(또는 `'boardrow'`)으로 지정하고 `rackKey`를 연결 → 5개 JSON(device-connections/rack-layout/board-face/board-info/measure-points)을 다시 임베드해서 새 시안으로 재빌드 → Playwright 등으로 클릭 경로 검증 후 project_write + SendUserFile로 전달.
7. 만들어진 JSON들을 python으로 검증(`json.load`로 파싱 확인 + 참조하는 boardRef/measurePointRef가 board-info.json/measure-points.json에 실제로 존재하는지 교차확인).
8. 완료 후 프로젝트의 최신 인수인계서(`claude/장비구성뷰_UI개선_인수인계서_갱신본_*.md`)에 이번 작업 내용을 새 섹션으로 추가(전체 다시 읽고 project_write) — 다른 채팅이 나중에 이어볼 수 있게 남겨두는 것.

## 3. 파일별 스키마 (필드 이름 그대로 맞출 것)

### claude/rack-layout.json
```json
{
  "schemaVersion": "1.0",
  "station": "전역 공통",
  "scopeNote": "...",
  "racks": {
    "SICAS": { "...": "기존 내용 유지" },
    "새그룹키": {
      "title": "OO 캐비닛 구성도",
      "note": "실제 배치 설명, 원본자료 출처",
      "boards": [
        { "row": "A", "side": "전면", "label": "표시 라벨", "boardRef": "board-info.json의 id", "count": 1 }
      ],
      "channelFrames": {
        "프레임명": { "title": "...", "boardOrder": ["보드id1","보드id2"], "note": "..." }
      },
      "powerFlow": [
        { "stage": "단계명", "desc": "설명", "measurePointRef": ["MP_..."], "boardRef": "..." }
      ]
    }
  }
}
```
- row 기반 `boards` 배열(각 항목이 캐비닛의 한 행)이 표준 스키마임 — 채널 반복 구조가 있으면 `frameRef`로 `channelFrames`를 가리키게 하고, 없으면 `boardRef`+`count`만 써도 됨.
- `boardRef`/`measurePointRef`는 반드시 board-info.json / measure-points.json에 **실제로 존재하는 id**만 쓸 것. 없는 정보를 지어내지 말고, 모르면 `note`에 "미확인, 원본자료 대조 필요"로 남길 것.

### claude/board-face.json (선택 — 없어도 v3가 자동 렌더링함)
```json
{
  "boards": {
    "새보드id": {
      "boardRef": "board-info.json의 id와 동일",
      "title": "보드 이름",
      "boardShape": "standard_eurocard_top_led",
      "note": "이 LED 정보 출처",
      "leds": [
        { "id": "고유id", "label": "LED명", "x": 0.3, "y": 0.15, "meaning": "...", "normalState": "...", "sourceRef": "boardInfo 또는 measurePoint(id)" }
      ]
    }
  }
}
```
- `x`,`y`는 0~1 좌표(좌상단 기준).
- LED 정보는 **반드시 board-info.json의 ledInfo 또는 measure-points.json의 ledCheck에서 그대로 가져올 것** — 새로 창작 금지.

### claude/device-connections.json
```json
{
  "nodes": [
    { "id": "SICAS", "...": "기존 내용 유지" },
    { "id": "새노드id", "label": "...", "rackRef": "rack-layout.json의 그룹키(있으면)", "group": "분류명" }
  ],
  "edges": [
    { "from": "...", "to": "...", "cable": "케이블 종류", "via": "경유장치(없으면 null)", "protocol": "...", "boardRefs": ["..."], "note": "출처/근거" }
  ]
}
```
- 연결 정보는 사용자가 준 이미지(시스템 Block Diagram 등)에서 확인된 것만 반영. 확실하지 않으면 `note`에 "미확인" 명시.
- 이미 이 그룹을 가리키는 노드가 있을 수 있음 — 중복 생성하지 말고 그 노드에 살을 붙이는 식으로.

## 5. 지켜야 할 규칙 (충돌 방지)

- **여러 그룹 채팅을 동시에 열어놓고 같은 파일(rack-layout.json, device-connections.json, 장비구성뷰_v3_시안.html 등)을 동시에 저장하지 말 것.** 프로젝트 문서는 부분수정이 아니라 전체 덮어쓰기 방식이라, 나중에 저장하는 쪽이 먼저 것을 지울 수 있음. 한 그룹을 끝내고 project_write까지 마친 뒤 다음 그룹으로 넘어가는 걸 권장.
- 모든 새 데이터는 **project_read로 최신본을 먼저 읽은 뒤, 그 위에 추가해서 전체를 다시 project_write**하는 방식만 사용.
- 없는 정보를 추측해서 채우지 말 것 — 모르면 `note`/`verify` 필드로 남기고 사용자에게 원본자료를 요청.
- 완료 후 최신 인수인계서에 작업 내용 기록 남기기(다른 채팅이 이어볼 수 있도록), 그리고 만들어진 파일(JSON·HTML)은 프로젝트 저장뿐 아니라 SendUserFile로도 다운로드 전달할 것.
